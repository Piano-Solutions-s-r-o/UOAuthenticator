# User Avatars — Uploads, Provider Images, and Generated Fallbacks

This document is the authoritative specification for the UOA avatar system. It supersedes
the original brief rules "no local avatar storage" (brief §2, §15, §20) and qualifies the
avatar update policy (brief §22.7). See the dated addendum in `Docs/brief.md`.

---

## 1. Overview

Every user always has an avatar image. The API resolves it with a fixed precedence:

1. **Uploaded** — an image the user (or their product backend) set through UOA.
   Stored in Postgres (`user_avatars` table). Takes precedence over everything.
2. **Provider** — the external avatar URL captured from a social provider
   (`User.avatarUrl`, unchanged behaviour: overwritten on every social login).
   Served by **server-side proxy** so callers always receive image bytes.
3. **Generated** — a deterministic, non-AI SVG generated by UOA. Always available,
   so every avatar GET endpoint returns an image with `200` for a known user.

Avatar **GET endpoints always return an image**, never JSON. Mutation endpoints
(`PUT`/`DELETE`) return the standard JSON envelope.

---

## 2. Generated avatar styles

Four styles, implemented as dependency-free server-generated SVG. Generation is
**deterministic per user**: seeded from a djb2 hash of the user id (the same hash
contract as `Auth/src/utils/workspace-icon.ts`), so a user's generated avatar is stable
across requests and instances, and cache-friendly.

| Style   | Description |
| ------- | ----------- |
| `tiles` | Symmetric identicon-style mosaic: 5×5 grid, mirrored vertically, two seed-derived colours on a light background |
| `waves` | Three to four stacked wavy bands (cubic Bézier paths) in seed-derived hues |
| `rings` | Concentric rings with seed-varied radii, stroke widths, and an offset centre |
| `mono`  | Black-and-white preset: seed-picked geometric pattern (diagonal stripes or quarter-circle truchet tiles), no colour |

Colour derivation follows the existing workspace-icon contract:
`hue = djb2(userId) % 360`, saturation 55%, lightness 45%, with fixed hue offsets for
secondary colours. `mono` uses only black/white/greys.

**Style selection order:**

1. `?style=` query override on the GET endpoints (one of the four values) — lets
   products preview or pin a style per call.
2. The signed config claim `avatars.default_style` for the domain (see §4).
3. Neither present → a stable pseudo-random pick: `styles[djb2(userId) % 4]`.

SVG responses accept an optional `?size=` (default 128, clamped 16–512), which sets the
SVG `width`/`height` (the `viewBox` is constant). Raster images (uploads, proxied
provider images) are always served as stored — `size` is ignored for them.

## 3. Storage model

New Prisma model (additive migration, no changes to existing tables):

```prisma
model UserAvatar {
  id          String   @id @default(cuid())
  userId      String   @unique @map("user_id")
  contentType String   @map("content_type")
  data        Bytes
  sizeBytes   Int      @map("size_bytes")
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @updatedAt @map("updated_at")

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@map("user_avatars")
}
```

- Stored in Postgres `bytea` — no filesystem or GCS dependency, safe on Cloud Run.
- One row per user; upload replaces the existing row content.
- RLS: mirror the policy pattern of the existing per-user child tables from the
  `20260423000001_rls_enable_policies` migration family (avatar reads/writes run on the
  admin Prisma client on domain-hash/admin paths, like the other pre-tenant-context reads).
- `User.avatarUrl` is untouched: it remains the provider URL, overwritten on every
  social login exactly as before (brief §22.7). Uploaded avatars are deliberately kept
  in a separate table so a later social login cannot clobber them.

### Upload validation

- Accepted types: **PNG, JPEG, WebP** — validated by **magic bytes**, not the client
  mimetype. The sniffed type wins and is what gets stored in `contentType`.
- SVG and any non-raster upload is rejected (stored-XSS surface). Generated SVGs are
  server-authored only.
- Max size: **1 MiB** (constant `AVATAR_MAX_BYTES` in `config/constants.ts`).
- Multipart field name: `file` (same convention as the signature PDF upload).
- All rejections use the standard generic error envelope (no format specifics leaked).

## 4. Config claim

New optional claim in the signed client config JWT:

```json
"avatars": {
  "default_style": "waves"
}
```

- `default_style` — optional, one of `tiles | waves | rings | mono`. Sets the domain's
  default generated-avatar style. Absent → stable per-user pseudo-random style.
- Validated in `ClientConfigSchema` (`config.service.ts`) following the `login_flow`
  pattern; added to the config-verifier redaction allowlists and to the config
  documentation blocks (`config-docs.ts`, `/llm`, `/api`).
- Unknown values reject the config exactly like any other invalid claim.

## 5. Endpoints

### Domain server-to-server (auth: domain hash bearer + `?domain=`, `/domain/*` family)

| Method | Path | Returns |
| ------ | ---- | ------- |
| GET    | `/domain/users/:userId/avatar` | **Image bytes** (uploaded \| proxied provider \| generated SVG). Query: `style?`, `size?` |
| PUT    | `/domain/users/:userId/avatar` | JSON `{ ok, avatar: { source, content_type, size_bytes, updated_at } }` — multipart upload sets the user's uploaded avatar |
| DELETE | `/domain/users/:userId/avatar` | JSON `{ ok: true }` — removes the uploaded avatar (resolution falls back to provider/generated) |

The `:userId` must resolve to a user visible to the authenticated domain under the same
semantics as `GET /domain/users` (user-scope aware). Unknown or cross-domain user ids
return the standard generic 404 — no enumeration signal beyond what `GET /domain/users`
already provides to that authenticated backend.

`GET /domain/users` additionally gains an additive `avatar_source` field per user:
`"uploaded" | "provider" | "generated"`. Existing fields (including `avatar_url`) are
unchanged.

### User self-service — "set it in our SSO" (auth: domain hash bearer + `X-UOA-Access-Token`, dual-auth like `/org/*` but without org-features gating)

| Method | Path | Returns |
| ------ | ---- | ------- |
| GET    | `/avatar/me` | **Image bytes** for the access-token subject. Query: `style?`, `size?` |
| PUT    | `/avatar/me` | JSON — multipart upload sets the caller's own avatar |
| DELETE | `/avatar/me` | JSON — clears the caller's own uploaded avatar |

The access token's `domain` claim must match `?domain=`. The acting identity is always
the token subject — a product backend relays the end-user's own choice here, while the
`/domain/users/:userId/avatar` routes are for backend-driven administration.

### Admin panel (auth: admin superuser bearer, `/internal/admin/*` family)

| Method | Path | Returns |
| ------ | ---- | ------- |
| GET    | `/internal/admin/users/:userId/avatar` | **Image bytes** — same resolution pipeline, for any user. Query: `style?`, `size?` |

Admin user summaries (`GET /internal/admin/users`, `/users/:userId`, `/search`) gain an
additive `avatarSource` field so the UI can label where the image came from.

## 6. Image response contract

Every successful avatar GET returns:

- `Content-Type`: `image/svg+xml; charset=utf-8` (generated) or the stored/sniffed
  raster type (uploaded/proxied).
- `X-UOA-Avatar-Source`: `uploaded | provider | generated` — metadata without a JSON
  side-channel.
- `Cache-Control: private, max-age=300` for uploaded/proxied; `private, max-age=86400`
  for generated (deterministic). `ETag` on uploaded (content hash) and generated
  (seed+style+size hash) responses.
- `X-Content-Type-Options: nosniff` and `Content-Disposition: inline; filename="avatar.<ext>"`.
- SVG responses additionally send
  `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'`.

### Provider proxying

When resolution lands on the provider URL, UOA fetches it server-side and streams the
bytes back so the caller still receives an image:

- HTTPS only; destination passes the existing SSRF safeguards (`utils/ssrf.ts`).
- Timeout ~5s, response capped at 5 MiB, response content type must sniff as a raster
  image.
- **Any failure falls back to the generated avatar** — the endpoint still returns 200
  with an image, and `X-UOA-Avatar-Source: generated`.
- No provider bytes are persisted (keeps brief §22.7's no-caching spirit).

## 7. Admin panel integration

- The shared `Admin/src/components/ui/Avatar.tsx` gains image support (initials remain
  the loading/error fallback). A `useUserAvatarQuery(userId)` hook fetches
  `/internal/admin/users/:userId/avatar` as a blob through the shared admin API client
  (bearer auth — plain `<img src>` cannot carry it) and renders an object URL.
- User-identity surfaces switch to the image-backed avatar wherever a real `userId`
  exists: users list, user detail header, superusers, org/team member tables, domain
  users tab, feature-audience members, and the global `UserDetailsModal` (whose private
  Avatar fork is consolidated into the shared component).
- Org/team/domain square avatars are unchanged (different concept).
- User detail surfaces the `avatarSource` label (Uploaded / From provider / Generated).

## 8. Security summary

- Uploads: raster-only, magic-byte sniffed, 1 MiB cap, generic errors, rate-limited
  mutations keyed per domain+user.
- Provider fetches: SSRF-guarded, HTTPS-only, size/time-capped, fail closed to the
  generated image.
- Generated SVG: server-authored, no scripts/foreign objects, served with `nosniff` and
  a restrictive CSP.
- No email enumeration: avatar routes identify users by id only, under credentials that
  can already list those users.
- The per-domain hash bearer, access tokens, and admin bearers follow the existing
  middleware; no new credential types.

## 9. Backwards compatibility

- No existing endpoint changes shape except additive fields (`avatar_source`,
  `avatarSource`).
- `User.avatarUrl` semantics are untouched; social login keeps overwriting it.
- The new config claim is optional; configs without it remain valid.
- The `user_avatars` table is additive; no data migration.
